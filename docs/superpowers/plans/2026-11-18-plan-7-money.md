# Plan 7: Money (Ledger, Cash Cycles, Wallet, Cash-outs) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax. This plan touches payment logic: CLAUDE.md "Risky changes" applies — every migration states its undo; nothing touches live data (local only).

**Goal:** Every pound is traced: delivering, returning or failing an order books balanced, append-only ledger entries; each Cairo day closes into a cash cycle; merchants see their wallet (balance, breakdown, transactions, cash cycles, cash-outs with proof of transfer); cash-outs are prepared on the merchant's schedule, approved by a second person and marked paid with the bank reference.

**Architecture:** New `src/money` domain. Double-entry ledger: `LedgerAccount`, `LedgerEntry` (unique idempotency key), `LedgerLine` (signed integer piastres). Database guarantees: entries and lines append-only (triggers); a deferred constraint trigger rejects any entry whose lines don't sum to zero. Balances are always summed from lines, never stored. Bookings for an order are posted inside the same transaction as its status change (`changeOrderStatus` calls `postOrderOutcome`).

**Spec:** design §7.5 Money and "What gets booked", §8 Wallet, §9 (integration test: create → deliver → cycle → cash-out → proof), §10 (VAT 14%, return fee 50%, no cash-out fee). GOAL §6 items 5–6. ## Accounts and bookings (exact)
Accounts: `merchant_wallet:<merchantId>` (liability: credit = Shiply owes the merchant), `cash_in_transit` (asset: cash held by couriers/hubs; split per courier and hub safe comes with operations), `bank` (asset), `revenue_shipping`, `revenue_fees` (open package, COD fee, insurance), `revenue_return_fees`, `vat_payable`.
1. **Delivered** (deliver, pick & choose, exchange, sign & return, cash collection *collect*): if cash > 0: Dr cash_in_transit / Cr wallet = cash. Fees: Dr wallet = order total fee; Cr revenue_shipping = shipping; Cr revenue_fees = open package + COD fee + insurance; Cr vat_payable = VAT. Key `order:<id>:delivered`.
2. **Cash collection *give* or Return with refund, delivered**: Dr wallet / Cr cash_in_transit = refund amount, plus the fee booking as in 1.
3. **Returned (to merchant, failed for good)**: return fee = 50% of frozen shipping (`return_fee_basis_points`); Dr wallet = shipping + return fee + VAT on both (VAT basis points); Cr revenue_shipping, revenue_return_fees, vat_payable. Key `order:<id>:returned`. Canceled before pickup books nothing.
4. **Cash-out paid**: Dr wallet / Cr bank = amount. Key `cash_out:<id>:paid`.
All amounts come from the order's frozen fee columns and settings at booking time; rounding half up once per line (`basisPointsOfPiasters`).

## Decisions (Claude's calls)
1. **Cash cycle** = one per merchant per Cairo day, closed by `closeCashCycles(dateCairo)` (idempotent; run nightly at 23:59 Cairo by a scheduled job in production — here a function + a staff action). A cycle holds the day's delivered/returned entries: totals cash collected, fees, net.
2. **What can be cashed out** = wallet balance from closed cycles only (today's open cycle is shown as "processing").
3. **Schedule**: weekly = Monday; twice a week = Monday and Wednesday; daily = every working day (Sun–Thu). `prepareCashOuts(financeUser, dateCairo)` creates one `prepared` cash-out per merchant with a positive cashable balance and an active bank account; merchants with a negative balance get none.
4. **Approval** by a second person (finance or admin, not the preparer) → `approved`; **paid** with bank reference (+ optional uploaded receipt image/PDF stored under `storage/` locally, max 5 MB) → posts entry 4; **canceled** only before paid.
5. **Proof of transfer** is a page (printable) with Shiply details, merchant, bank (masked IBAN), amount, cycles covered, bank reference, paid date — as in the mockup `transferProof`; the uploaded receipt, if any, is linked.
6. Finance screens (prepare, approve, mark paid) live in the staff area (Plan 6, design pending owner); the functions are built and tested here.

## Global Constraints
Plans 1–5 constraints. Money only in integer piastres. No balance column anywhere. Every posting idempotent by key; the database rejects unbalanced entries and any UPDATE/DELETE on entries/lines.

## Review Focus
1. **The same delivery confirmed twice** (double click, retry) → booked once. Task 2.
2. **Two finance people paying the same cash-out at once** → paid once. Task 4.
3. **A merchant whose balance is negative** (more fees than cash) → no cash-out, balance shown negative. Task 4.
4. **Rounding**: sum of lines always zero for odd amounts (e.g. shipping 6801). Task 1.
5. **Cycle close run twice for the same day** → no duplicate cycle. Task 3.
